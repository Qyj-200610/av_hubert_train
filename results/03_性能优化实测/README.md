# 03 性能优化实测（A/B 数据）

> 这一份是"为了让整套流程跑得动、跑得快"所做的优化的**实测依据**。
> 每条都写明：怎么量的、量到了什么、有没有副作用。方法论细节见
> `../../docs/训练加速与阻塞修复记录.md`。

## 1. 分片并行：8 核从只用 1 核 → 6–6.6×

原 `pipeline_lrs2.sh` 的各 rank 是**串行**执行（脚本自己还会打印"建议按 rank 并行"的提示），
8 核配额实际只跑 1 核。

| 指标 | 串行（实测） | 8 rank 并行（实测） |
| --- | --- | --- |
| 关键点阶段吞吐 | 0.45 it/s（2.236 s/clip） | **2.7–3.0 it/s** |
| 加速比 | — | **5.9× – 6.6×** |
| CPU 占用 | 约 1 核 | 8 个 rank 各约 88–90% CPU（合计约 7.2/8 核） |

- 关键点阶段实测：串行 ≈ **30 小时**（48,164 × 2.236 s ≈ 29.9 h）（不是方案初稿里写的 75 分钟——那份估算漏乘了分片数），
  并行后实测 **4.4 小时**。
- 采用**按步数**（`optimization.max_update`）而非按 epoch 的验证频率，
  避免小样本下每个 epoch 都验证。

## 2. 预解码帧缓存：数据加载 0.83 → 0.67 秒/步

训练时每条 clip 都要现解 mp4。实测单 clip 的解码开销拆解：

| 环节 | 耗时 |
| --- | --- |
| `cv2.VideoCapture` 打开 | 4.1 ms |
| **逐帧 `cap.read()` 解码** | **12.1 ms** |
| `cvtColor(BGR2GRAY)` 逐帧 | 0.6 ms |
| `np.stack` | 0.4 ms |
| **合计** | **17.2 ms/clip** |

一个 4000-token 的 batch 约 80 条 → 光解码就 1.3 秒。于是把全部 ROI 帧预解码成
一个大文件 + 索引，训练时内存映射读取（未命中自动回退在线解码）。

| 变体（真实规模：3,000 条，批量 69 条/步） | 40 步墙钟 | 每步 |
| --- | --- | --- |
| 现解 mp4（8 worker） | 33.3 s | 0.83 s |
| **帧缓存（8 worker）** | **26.7 s** | **0.67 s** |

- 批量大小：`max_tokens=4000` → 实测 `bsz = 69.2` 条/步。
- **保真度：缓存帧与在线解码逐位一致**（抽样 30 条，0 条不一致；
  构建器直接调用训练用的同一个 `load_video`，不是"等价实现"）。
- **代价（更正）**：缓存文件实测 **24.07 GB**（2,611,599 帧 × 96×96 字节），
  不是早先文档里写的"211 MB"（那是算错了，96×96 少乘了一次 96）。
- **⚠ 这套 A/B 是在 CPU 被预处理占满时测的，与真实训练条件不同。**
  真实训练（CPU 空闲、**且因索引发布失败而完全没用缓存**）实测 **0.33 秒/步**
  （3.0 步/秒），比上表"带缓存 0.67 秒/步"还快 2 倍；训练期间 **GPU 利用率 100%**，
  说明该负载是 **GPU 瓶颈**，数据加载并非限制项，**帧缓存对本任务的收益有限**。
  教训与 §6 一致：**测优化必须在真实条件下测**，否则会把优先级排错。

## 3. 唇部 ROI：单 clip 1.35 → 0.63 秒（2.1×）

| 优化 | 前 | 后 | 保真度（隔离实测） |
| --- | --- | --- | --- |
| 重采样 skimage → `cv2.warpAffine` | 535 ms | **121 ms（4.4×）** | 解码前 ROI 帧：平均差 0.503 灰度级、最大 3、>2 占 **0.001%** |
| 写视频逐帧 PNG + concat → rawvideo 管道 | 350 ms | **244 ms** | 与官方逐帧 PNG **逐位一致**（平均差 0.000、最大 0） |

- 上表是**单进程、CPU 争抢下**的 A/B。真实生产运行时 8 rank 并行、CPU 空闲：
  **全量 48,164 条实测 37.7 分钟**，即每 rank 有效 **0.38 秒/clip**
  （48,164 ÷ 37.7 分钟 ÷ 8 rank）。按 A/B 的 2.1× 比例推算，不换 cv2 约需 1.3 小时以上。
- **诚实说明**：解码前的 0.5 灰度级差异经 h264 有损编码后放大到产物层面平均 2.26 灰度级
  （约 0.9%，与压缩噪声同量级，对训练影响可忽略）；但产出的 ROI 视频与官方预处理
  **不再逐位可比**。要完全退回官方行为：`--warp-backend skimage --write-backend png`。
- 另一处**被否决**的优化：想用 `frame[:,:,0]` 代替 `cvtColor`（以为 ROI 是灰度图）。
  实测否决——ROI 视频**不是**灰度，1592 帧全部三通道不等、最大通道差 **113**，
  两条路径输出逐位不一致。幸好验证了等价性，否则会静默改变训练数据。

## 4. 数据加载吞吐基准（CPU 被预处理占满时测得，属偏悲观口径）

| 进程数 | 200 个样本 | 吞吐 |
| --- | --- | --- |
| 1 | 6.4 s | 31.4 clips/s |
| 4 | 1.9 s | 107.3 clips/s |
| 8 | 1.8 s | **108.6 clips/s（饱和）** |

单样本平均 **16.1 ms / 67 帧**。
（另：构缓存时 CPU 空闲，实测约 **310 clips/s**，可见争抢对数据管线影响很大。）

## 5. 解码吞吐

真实训练完的这次解码（beam=10，原始日志）：

| 口径 | 句数 | 耗时 | 速度 |
| --- | --- | --- | --- |
| `test` | 1,243 | **22.9 秒** | 54.29 句/秒 |
| `test_mv` | 246 | **6.0 秒** | 40.98 句/秒 |

（早先在小样本上测到 6.47 句/秒并据此推算"test 约 3 分钟"，**实际快了约 8 倍**；
小样本那次包含了启动与预热开销，不具代表性。官方 `beam=50` 约慢 5 倍。）
**结论：解码不是瓶颈，训练才是。**

## 6. 一个测量方法上的坑（值得记）

第一次给小样本计时得到"4.2 秒/步"，看起来训练很慢。实际是**假象**：
小数据集 30 条训练样本 2 步就是一个 epoch，而 fairseq 每个 epoch 都要重建 DataLoader，
且每个 checkpoint 有 1.9 GB、写盘要 5–7 秒，把耗时全淹了。
关掉存盘（`checkpoint.no_save=true`）后才是真实的 1.3 秒/步。
后来构造"足够大"的合成数据集（复制 tsv 行到 3,000 条）才量到有代表性的
**0.67–0.83 秒/步**。

> 教训：**计时必须先把 I/O 噪声摘掉，并且让 epoch 长度接近真实规模**，
> 否则量到的是噪声不是性能。

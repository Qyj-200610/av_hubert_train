## 3. 关于抽音频这一步（多余步骤，已确认）

纯视觉任务不需要音频 wav，依据（`avhubert/hubert_dataset.py`）：

- `:283,359` 只有 `'audio' in self.modalities` 时才读 wav；
  tsv 的音频列只被当**字符串**用来取 utterance id（`:64-67`、`:363`）；
  **音频帧数那一列（`items[-1]`）全程没有被读过**（全仓库 grep 确认）。
- 因此 `pipeline_lrs2.sh` 现在默认 `MODALITY=video`，直接跳过整步抽音频
  （复跑可省约 67 分钟 + 3.3 GB）。本次运行的音频是改动前留下的，不影响结果。

## 4. 关于唇部 ROI 只用 37.7 分钟

这一阶段原本预计 2 小时以上（单 clip 约 1.2–1.5 秒，逐帧 skimage 相似变换 + 逐帧 PNG 落盘）。
在它即将开跑前做了两处优化并**逐位校验**后启用：

| 优化 | 实测 | 保真度 |
| --- | --- | --- |
| 重采样 skimage → `cv2.warpAffine` | 535 ms → 121 ms（**4.4×**） | 解码前 ROI 帧平均差 **0.503** 灰度级、最大 3、**>2 的像素占 0.001%** |
| 写视频「逐帧 PNG + concat」→ rawvideo 管道 | 350 ms → 244 ms | **逐位一致（平均差 0.000，最大 0）** |

> 需要说明：这两处微小差异经 h264 有损编码后会被放大（产物层面平均差 2.26 灰度级，
> 约 0.9%，与压缩噪声同量级）。要完全退回官方行为可加
> `--warp-backend skimage --write-backend png`，代价是这一阶段回到 1.5 小时以上。

## 6. 全量完整性验证（逐条核对 48,164 条，脚本 `scripts/verify_dataset.py`）

复跑方式（在实例上）：
```bash
source /hy-tmp/avh_env.sh
cd /hy-tmp/av_hubert_train
python scripts/verify_dataset.py --work-dir /hy-tmp/lrs2_data --workers 8   # 约 45 秒
```

除了"数文件个数"，还验证了 manifest 的**核心契约**——因为这三者一旦不一致，
训练**不会报错**，只会静默用错长度的样本或错的分批：

```
tsv 里的视频帧数 items[-2]  ==  landmark pkl 的条数  ==  ROI 视频的实际帧数
（hubert_dataset.load_audio_visual 用 items[-2] 做样本过滤与分批；
  align_mouth.crop_patch 用 len(landmarks) 当循环上界）
```

| 检查项 | 结果 |
| --- | --- |
| 逐条核对 | **48,164 条全部检查**（不是抽样） |
| 三方帧数/条数不一致 | **0 条** |
| ROI 尺寸不是 96×96 | **0 条**（分布：`{(96,96): 48164}`） |
| landmark 读取失败 / ROI 打不开 | **0 条** |
| 无脸帧（检测到 `None` 的帧） | 12,948 帧，占 2,611,599 帧的 **0.5%**（由 `landmarks_interpolate` 插值填补） |
| 各 split tsv 行数 / 列数 | train 45,839 / valid 1,082 / test 1,243 / test_mv 246，**全部 5 列** |
| tsv 内重复 id | **0** |
| tsv 视频路径指向的文件缺失 | **0** |
| tsv 帧数列与 `nframes.video` 不符 | **0** |
| train∩valid、train∩test、valid∩test | **均为 0**（无测试泄漏） |
| `test_mv` 是否为 `test` 子集 | 是（246 / 1,243） |

> 另有一条"用推理代替检查"的结论：抽帧阶段若单条失败，`align_mouth.py` 会记入失败清单
> 并以非 0 退出，从而让流水线中止；流水线正常跑完（`video/` = 48,164 = `file.list`），
> 说明**没有任何一条 landmark 读取失败**——上面的逐条检查把这条推论也证实了。

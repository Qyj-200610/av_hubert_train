# 微调加速与阻塞修复记录

> 目标：在**单张 RTX 3090** 上把 LRS2 的 AV-HuBERT 微调跑起来，并尽量压缩训练时间。
> 本文记录实测数据、改了什么、以及为什么这么改。

## 0. 先说结论

| 事项 | 结果 |
| --- | --- |
| 训练原本**根本跑不起来** | 发现并修复 **7 个**独立阻塞（训练 5 个 + 解码 2 个，见 §2） |

## 1. 为什么原来的配置"看起来对、其实很慢"

原 `base_lrs2_video_only.yaml` 是 **large 模型配置的副本**：它逐项等于
`finetune/large_vox_433h.yaml`。

| 参数 | 原 LRS2 配置 | 官方 **base**（`base_vox_433h`） | 官方 large |
| --- | --- | --- | --- |
| `max_update` | 30000 | 45000 | 30000 |
| `freeze_finetune_updates` | 30000（=全程冻结） | 22500（**一半，后半程解冻**） | 30000 |
| `decoder_layers` | 9 | 6 | 9 |
| `decoder_embed_dim` | 1024 | 768（默认） | 1024 |
| `decoder_ffn_embed_dim` | 4096 | 3072 | 4096 |
| `decoder_attention_heads` | 8 | 4 | 8 |

而本项目的预训练权重是 **base**。已用 state_dict 实测确认（`encoder.layers.0.self_attn.k_proj.weight` 为 768×768、`fc1` 为 3072×768、共 **12 层**）：

```
编码器层数: 12
编码器 embed_dim: 768      <- base
编码器 ffn_dim: 3072
```

于是形成 **base 编码器 + large 解码器** 的错配：
- 解码器参数量约 **151M**，官方 base 解码器约 **57M**（**2.6 倍**）；
- 维度不等会让解码器 cross-attention 的 `k_proj` 尺寸不匹配（**真正的后果见 §2.4，第一次前向就崩**）。
  （更正：早先这里写「多建一层 768→1024 投影」是**错的**——`hubert_asr.py:319` 那个 proj
  属于 `HubertEncoder`，只有 CTC 分支 `AVHubertCtc` 会用；seq2seq 走 `HubertEncoderWrapper`，没有 proj。）

**所以"把解码器改回 768/3072/6/4"不是降质，而是回到官方 base 配方**，同时每步更快。

## 2. 五个阻塞（都会让训练立刻失败）

这五个都是"没真跑过就不知道"的问题——实例上**从未有过 `exp/` 目录**，说明训练路径此前一次都没跑通。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `找不到 sentencepiece 模型: .../data/spm1000/...` | 流水线把词表写在 **`<work_dir>/spm1000/`**（`lrs2_manifest.py:98`），而 `DATA` 指向 `<work_dir>/data`，默认路径差一级 | `run_finetune.sh` 里按 `$DATA/spm1000`、`$DATA/../spm1000`、`$DATA` 依次探测 |
| 2 | `Could not override 'common.user_dir' ... Key 'common' is not in struct` | 配置头部 `# @package _group_`：Hydra ≥1.1 里 `_group_` 指"配置所在分组目录"，本文件在 `conf/finetune/` 下，所有键被挂到 `finetune.*` | 改为 `# @package _global_` |
| 3 | `omegaconf.errors.ConfigAttributeError: Missing key reset_logging` | fairseq 的 `add_defaults` 只补 `Any` 类型分组（task/model/criterion/optimizer/lr_scheduler）；`common`/`checkpoint`/`dataset`/`distributed_training` 的默认值本来靠 fairseq 自带主配置提供，用 `--config-name finetune/xxx` 换掉主配置后就缺字段 | 新增 `scripts/make_full_config.py`，先把这些分组补成完整字段集再训练（不依赖 hydra 版本） |
| 4 | `AssertionError: Could not infer task type from {'_name': 'av_hubert_pretraining'...}` | `common.user_dir` 指到了仓库根目录。fairseq `utils.py:479` 会 `os.path.split(user_dir)` 后 import **最后一级目录名**，必须是可导入的包——也就是 `avhubert/`（它的 `__init__.py` 才注册 task/model）。上游 README 先 `cd avhubert` 就是这个原因 | `USER_DIR="${REPO_ROOT}/avhubert"` |
| 5 | `AttributeError: module 'omegaconf._utils' has no attribute 'is_primitive_type'` | 环境里是 **hydra-core 1.3.7 + omegaconf 2.3.1**，而 `fairseq/setup.py` 明确要求 `hydra-core<1.1`、`omegaconf<2.1`（fairseq 自己 monkey-patch 了 `_utils.is_primitive_type`，新版本已删除该属性） | `pip install "hydra-core==1.0.7" "omegaconf==2.0.6"`（连带 `antlr4-python3-runtime` 4.9.3→4.8）。只动 3 个纯 Python 包，且预处理流程不依赖 hydra/omegaconf，不影响正在跑的流水线 |

### 2.1 解码路径还有两个坑（同样让 WER 出不来）

## 3. 快速配置做了什么（`base_lrs2_video_only_fast.yaml`）

| 项 | 原值 | 快速值 | 依据 |
| --- | --- | --- | --- |
| `optimization.max_update` | 30000 | **8000** | 步数与墙钟近似线性 |
| `lr_scheduler.warmup_steps / decay_steps` | 10000 / 20000 | **2000 / 6000** | 保持官方 warmup:decay = 1:2 |
| `optimization.lr` | 0.001 | **0.002** | batch ×4 后按 sqrt 规则放大；不稳可退回 |
| `dataset.max_tokens` | 1000 | **4000** | 编码器全程 `no_grad`，显存只由解码器决定，24G 放得下大 batch |
| `dataset.num_workers` | 6 | **8** | 上限=容器 CPU 配额 |
| `validate_interval` | 2（按 epoch） | **100**（等于关掉）+ `validate_interval_updates: 2000` | 按步验证，开销可预期（不能填 0，会除零） |
| `decoder_layers / embed / ffn / heads` | 9 / 1024 / 4096 / 8 | **6 / 768 / 3072 / 4** | 回到官方 base 配方；768 是**能跑**的前提（原值会让 cross-attention 的 k_proj 尺寸不匹配，见 §2.4） |
| `freeze_finetune_updates` | 30000 | **8000**（= max_update） | 编码器全程冻结 = 唯一参与反传的是解码器 |

**关键的"等价换算"**：数据曝光量
原配置 30000 步 × 1000 tokens = **30M**；快速配置 8000 步 × 4000 tokens = **32M**。
**看的数据几乎一样多，但优化步数少 3.75 倍。**

另外 `AVHubertSeq2Seq.forward`（`hubert_asr.py:495`）在冻结期把编码器包在
`torch.no_grad()` 里，所以"全程冻结"同时省掉编码器的反向与激活显存。

## 4. 实测数据

### 4.1 端到端 20 步（小样本集，`/hy-tmp/lrs2_parcheck`，90 条）

| 指标 | 值 |
| --- | --- |
| 退出码 | **0**（含验证 + `checkpoint_best.pt` 落盘） |
| fairseq 自报 `done training in` | **35.5 秒 / 20 步** |
| `train_wall` | 25 秒 @18 步 → 36 秒 @20 步 |
| `train_ups` | 0.76 更新/秒（epoch 9 平均）→ **约 1.3 秒/步** |
| batch | `bsz` 15 条、`wpb` 241 词 |
| checkpoint 大小 | **1.92 GB / 个**（`checkpoint_last.pt` + `checkpoint_best.pt`） |

> 第一次计时得到"4.2 秒/步"是**假象**：小数据集上 30 条训练样本 2 步就是一个 epoch，
> 而每个 epoch 都要写一个 1.9 GB 的 `checkpoint_last.pt`（5–7 秒），把耗时全淹了。
> 关掉存盘后才是真实的 1.3 秒/步。**这也是个教训：计时必须先把 I/O 噪声摘掉。**

### 4.2 数据加载吞吐（同一时刻，CPU 被预处理占满）

| 进程数 | 200 个样本耗时 | 吞吐 |
| --- | --- | --- |
| 1 | 6.4 s | 31.4 clips/s |
| 4 | 1.9 s | 107.3 clips/s |
| 8 | 1.8 s | **108.6 clips/s（饱和）** |

单样本平均 **16.1 ms / 67 帧**（`cv2.VideoCapture` 逐帧解码 + BGR→灰度）。

### 4.3 解码吞吐（beam=10，30 句小样本）

```
Recognized 30 utterances (1428 tokens) in 4.6s (6.47 sentences/s, 307.88 tokens/s)
```

按 6.47 句/秒推算，LRS2 test 全量 **1,243 句约 3 分钟**；官方 `beam=50` 约慢 5 倍，
也就是十几分钟量级。**结论：解码不是瓶颈，训练才是**（beam 调小只是顺手省时间）。

---

### 4.4 真实规模的每步耗时（关键测量）

小样本集（90 条）测出的每步耗时**被严重高估**：30 条训练样本 2 步就是一个 epoch，
而 fairseq 每个 epoch 都要重建 DataLoader（重启 worker、重读标签、重跑
`load_audio_visual`）。真实数据一个 epoch 约 573 步，这部分开销会被摊薄。

于是构造了一个"足够大"的合成数据集来测（`train_optimize.py synth`：把 tsv/wrd 行
复制 100 倍、id 加后缀保证唯一、**视频路径不变所以帧缓存照样命中**），
3,000 条训练样本 ≈ 1.1 个 epoch，批量实测 `bsz = 69.2` 条/步：

| 变体 | 40 步墙钟 | 每步 | 每秒更新 |
| --- | --- | --- | --- |
| 现解 mp4（8 worker） | 33.3 s | **0.83 s** | 1.38 |
| **帧缓存（8 worker）** | **26.7 s** | **0.67 s** | 1.86 |

- 帧缓存收益 **1.25×**（真实规模下比小样本测出的 1.43× 略低——批量大了以后
  每步固定开销被摊薄，解码在总耗时里的占比下降）。
- 对比小样本测出的 1.07–1.53 s/步：**真实规模下每步只要 0.67 s**。

**按 8000 步推算：8000 × 0.67 ≈ 1.5 小时**（这是 CPU 被 8 个预处理 rank 占满时的推算）。
**真实运行结果：0.33 秒/步，8000 步只用 44.3 分钟**——比推算快一倍，
因为 CPU 空出来、且训练期间 GPU 利用率一直是 100%（是 GPU 瓶颈而非数据加载瓶颈）。

**结论：训练已经不是瓶颈了。** 原配置（30000 步 + large 解码器 + 无缓存 + 现解 mp4）
按同一口径估算 10 小时以上；实测 **44.3 分钟**（0.33 秒/步），**差 10 倍以上**。
既然预处理（数小时）才是主导，就没有必要再牺牲 WER 去砍训练步数。

## 5. 瓶颈定位与「预解码帧缓存」优化

### 5.1 定位过程

- 实测 1.3–1.5 秒/步、batch 15 条 → 约 11 clips/s，而加载基准在同样受限的 CPU 上能到 **108 clips/s**。
- 一个 15 条/1500 token 的 batch 在 3090 上纯 GPU 前反向应远低于 0.5 秒。
- **结论：训练循环是"数据加载/Python 开销"受限，GPU 大部分时间在等数据。**

把单个 clip 的 `load_video` 拆开看：

| 环节 | 耗时 |
| --- | --- |
| `cv2.VideoCapture` 打开 | 4.1 ms |
| **逐帧 `cap.read()` 解码** | **12.1 ms** |
| `cvtColor(BGR2GRAY)` 逐帧 | 0.6 ms |
| `np.stack` | 0.4 ms |
| **合计** | **17.2 ms/clip** |

> 顺带否掉了一个"看起来很美"的优化：想用 `frame[:,:,0]` 代替 `cvtColor`
> （因为 ROI 本该是灰度图）。**实测否决**——ROI 视频并不是灰度，
> 1592 帧里 1592 帧三通道不等，最大通道差 **113**；两条路径输出逐位不一致。
> 幸好验证了等价性，否则会静默改变训练数据。

### 5.2 做法：预解码成一个大文件 + 内存映射

ROI 帧总量实测约 **24 GB**（总帧数 2,611,599 × 96×96 字节）。
> 更正：早先这里写的是"≈ 211 MB"，那是**算错了**——96×96 少乘了一次 96，
> 实际大了两个数量级。24 GB 对本机 100 GB 的 `/hy-tmp` 仍然放得下，
> 但"缓存很小、几乎不占空间"这个说法不成立，磁盘占用要按 24 GB 计。
既然每步都要重复解码同一个文件，不如先解一次：

- `scripts/build_frame_cache.py`：多进程解码全部 clip → `<out>/frames.bin` + `<out>/index.npz`
  （keys / offsets / lengths / heights / widths）。
- `avhubert/utils.py` 新增 `FrameCache`：`np.memmap` 只读打开，**按 pid 惰性重开**
  （DataLoader 是多进程，fork 后必须各自打开）。未命中返回 `None`。
- `avhubert/hubert_dataset.py`：`load_video` 先查缓存，未命中**自动回退**到在线解码，
  所以缓存不完整只会变慢、不会出错。
- 新增 `task.video_cache` 配置项（默认 `null`，行为与原来完全一致）。
- **逐位复现**：构建器直接调用 `avhubert/utils.py:load_video`，不是"等价实现"；
  实测抽样 30 条，缓存帧与在线解码**逐位一致（0 条不一致）**。

### 5.3 实测收益（同样条件下 A/B，4 worker，CPU 仍被预处理占满）

| 变体 | 40 步训练墙钟 | 每秒更新 | 每步耗时 |
| --- | --- | --- | --- |
| 现解 mp4 | 61.2 s | 0.78 | 1.53 s |
| **帧缓存** | **42.6 s** | **1.29** | **1.07 s** |
| 收益 | — | **1.65×** | **1.43×** |

全量估算（按 80 clips/batch、640,000 次 clip 加载）：
在线解码约 **16 ms × 640,000 ≈ 2.8 小时**的纯解码开销被消掉。

**缓存没吃掉全部瓶颈**：加缓存后每步仍有约 1 秒，说明还有别的开销
（DataLoader 进程间传递的 float64 帧、`Normalize` 把 uint8 变成 float64
导致每批约 55 MB 的搬运、以及单进程 DDP 的 `find_unused_parameters` 开销等）。
这些要等预处理结束、CPU 空出来之后再测才能定位——**当前所有测量的 CPU 都被
8 个预处理 rank 占满，绝对数字偏悲观，但相对比较有效**。

### 5.4 怎么用

```bash
# 1) 数据流水线跑完后，先构建一次缓存（实测约 280 clips/s ≈ 3 分钟，产出约 24 GB）
python scripts/build_frame_cache.py \
    --work-dir /hy-tmp/lrs2_data --out /hy-tmp/lrs2_data/frame_cache \
    --workers 8 --verify 30        # --verify 会抽 30 条做逐位一致性校验

# 2) 训练时启用
task.video_cache=/hy-tmp/lrs2_data/frame_cache bash scripts/run_finetune.sh fast
```

**每个 epoch = 45839 / (4000/50) ≈ 573 步**（按 50 帧/clip 估）。

## 7. 已知取舍（写清，便于汇报）

1. **编码器全程冻结**：省掉编码器反向，是最主要的时间取舍；代价是编码器不适配新数据，
   WER 会比官方"后半程解冻"配方差一些。要贴近官方就把 `FREEZE_UPDATES` 设成一半。
2. **解码器缩回 base 尺寸**：这是**修错配**，预期不损质量（甚至更稳），但与原配置的
   实验结果不可直接对比。
3. **`beam` 调小**：WER 通常只差零点几个点，但必须写清用的 beam。
4. `find_unused_parameters: true` 必须保留（video-only 时音频分支参数未使用，DDP 会报错）。

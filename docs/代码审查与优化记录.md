## 1. 与任务要求的对照：哪些步骤是必需的，哪些是多余的

任务三的要求（`任务要求.md` §3.3）落地路线是：
**官方预训练权重 → 在 LRS2 main（train/val）上微调 → 在 LRS2 test 上测试（仅视觉模态）→ 报 WER**。
我们走的正是这条线，六步流水线逐步对照如下：

| 步骤 | 是否必需 | 依据 |
| --- | --- | --- |
| 1 解析列表（prepare） | ✅ 必需 | `Dataset.md` 明确要求按给出的三个列表改写；`test.txt` 是两列（路径 + NF/MV） |
| 2 **抽音频** | ❌ **多余**（见 §1.1） | 本任务只用视觉模态，音频 wav 从未被打开 |
| 3 dlib 关键点 | ✅ 必需 | `align_mouth.py` 有 `assert os.path.isfile(landmarks_pathname)` |
| 4 唇部 ROI | ✅ 必需 | 模型的视频输入 |
| 5 数帧 | ⚠️ 只需一半 | tsv 的**视频**帧数被 `load_audio_visual` 用来过滤/对齐；**音频**帧数列从未被读 |
| 6 manifest / 词表 | ✅ 必需 | 目标端 BPE 词典 `dict.wrd.txt` 必需 |

### 1.1 被确认多余的那一步：抽音频

`pipeline_lrs2.sh` 的 `step_audio` 花了约 **67 分钟**、产出 **3.3 GB** 的 wav。
但对「纯视觉」这条交付路线，这些文件根本没被读过：

- `hubert_dataset.py:283,359`：audio 只在 `'audio' in self.modalities` 时才加载；
  本配置 `task.modalities: ["video"]`，所以 `load_feature` 直接返回 `audio_feats = None`。
- `hubert_dataset.py:389-409`（collater）：`audio_source` 全为 None 时被置 None，
  音频尺寸回退用视频尺寸，`collated_audios = None`。
- tsv 的四列里，`hubert_dataset.py` 只读了 `items[0]`（id）、`items[1]`（视频路径）、
  `items[2]`（音频路径，**仅作为字符串**用于 `fid = ...split(':')[1]`）、
  `items[-2]`（视频帧数）。**`items[-1]`（音频帧数）从头到尾没有被读过。**
- 也就是说：只需要「音频路径那一列的字符串」，不需要文件本身，也不需要音频帧数。

**结论**：对纯视觉任务，`step_audio` 可以整步跳过，`count_frames` 也可以不算音频
（`count_frames.py:18` 读 wav 只为得到那个没人用的数字）。
代价是 `lrs2_manifest.py:79,91` 要求 `nframes.audio` 文件存在且长度一致，
所以要给一个占位值——这是一处**可优化但需要改代码**的点（见 §4 待办）。

> 本次运行音频已经抽完了，不追溯；但这条结论对「别人复跑」很有价值：
> 纯视觉路线能省 **1 小时出头的预处理时间 + 3.3 GB 磁盘**。

### 1.2 一处需要向评审说明的口径差异（不是 bug）

`任务要求.md` §3.3.5 写的是「**CTC 贪心解码**」，§3.3.6 又要求写明「**是否 beam search**」。
而官方仓库的微调配置（`base_vox_433h.yaml` 等）用的是 **seq2seq**（Transformer 解码器 +
beam search），论文里 LRS3 的主要结果也是 seq2seq。我们跟随**仓库自带配置**，
因此用的是 seq2seq，并在汇报里写清 beam 大小。这一点会在结果表里注明。

### 2.4 第二轮审查新增：一个"第一次前向就崩"的配置错误（已修并验证）

第 4 路审查（覆盖 `lrs2_prepare.py` / `lrs2_manifest.py` / `setup_env.sh` /
三个微调配置 / `hubert_dataset.py` 全文）报出了**本轮最重要的问题**，我复现确认后修复。

#### ★ `decoder_embed_dim: 1024` 配 base 编码器（768 维）→ 第一次前向直接抛异常

- `smoke_lrs2.yaml:110` 与 `base_lrs2_video_only.yaml:113` 写的是 **large** 的解码器尺寸
  （1024 / 4096 / 9 层 / 8 头），而本项目用的是 **base** 权重（编码器 768 维）。
- 根因链（审查给出，我逐条核对）：
  `AVHubertSeq2SeqConfig` 里**没有** `encoder_embed_dim` 字段（`hubert_asr.py` 中 0 处）
  → `fairseq/modules/transformer_layer.py:263` 的
  `kdim=getattr(args,"encoder_embed_dim",None)` 取到 `None`
  → `multihead_attention.py:43-44` 把 cross-attention 的 `kdim` 回退成
  `decoder_embed_dim=1024` → `k_proj = Linear(1024,1024)`
  → 而编码器 memory 只有 768 维 → 乘不上。
- **实测复现**（`olddec` 变体，把解码器改回 1024）：
  ```
  RuntimeError: mat1 and mat2 shapes cannot be multiplied (204x768 and 1024x1024)
  ```
  受影响的是 **`run_finetune.sh smoke` 与 `train`** —— 正好是 README 与 `setup_env.sh`
  让人照着跑的前两条命令。只有后写的 `fast` 配置能跑（因为 768 恰好等于编码器维度）。
- **修法**：解码器尺寸回到官方 base 默认值（768 / 3072 / **6** 层 / **4** 头），
  即删掉从 large 抄来的那几行覆盖；调度也回到官方 base
  （`max_update 45000` / `warmup 15000` / `decay 30000` /
  `freeze_finetune_updates 22500` = **一半**，官方是前半冻结、后半解冻）。
- **验证**：改完后用真实 smoke 配置跑通 20 步，退出码 0、
  `done training in 10.8 seconds`、**无形状错误**（这条路径还覆盖了
  `freeze_finetune_updates: 0` 的"编码器解冻"分支，是 `fast` 配置没走到的）。
- **顺带更正我自己写错的一条理由**：`fast` 配置注释里把 768 的收益说成
  "省掉 768→1024 投影层"（引 `hubert_asr.py:319`）。那个 `proj` 属于 `HubertEncoder`，
  只有 CTC 分支（`AVHubertCtc`）会用；seq2seq 走 `HubertEncoderWrapper`（`:471`），没有 proj。
  **768 不是"更快"，而是"能跑"的前提。** 注释已按事实改写。

#### 审查明确排除的项（本轮新增，均已逐条核对）

- 视频帧数列取 `items[-2]` 与写入端一致；**`items[-1]` 全程无人读**（全仓库 grep）。

- `collater` 的 `audio_source is None` 分支自洽（视频长度接管 `audio_size`，
  视频那次调用提供 `padding_mask`，`hubert.py:706-708` 在 `encoder_embed_dim` 宽度补零）。
- `find_unused_parameters: true` **必需**（video-only 时音频 SubModel 无梯度）。
- 数据划分干净：0 重复、两两交集为空、无共享 `video_id`；**MV = 246 / NF = 997**。
- 官方在**全部标签**（含 test 转写）上训练 sentencepiece 属上游行为，
  本项目保持一致，并在结果文档里主动披露。
- `max_sample_size: 500`、`test.txt` 两列处理、CRLF（三个消费端都 `strip`）
  等均与上游一致，不是 bug。

## 3. 性能优化与实测

### 3.1 唇部 ROI：warp 换 cv2（本轮最大的剩余收益）

`align_mouth` 单 clip 约 1.2–1.5 秒，其中 **`skimage.transform.warp` 占大头**。
官方的做法是每帧用 skimage 做相似变换到 256×256；实测把它换成 `cv2.warpAffine`
**快 4.4×**（535 ms → 121 ms，单进程、CPU 争抢下的相对值）。

**方向性陷阱**：`cv2.warpAffine` 默认就把 M 当作 src→dst 的**正向**映射（内部自己求逆），
所以直接传 `tform.params[:2, :]`，**不能再 `invertAffineTransform`**。
第一版双重求逆，画面整体错位，ROI 平均差 80 个灰度级——这类错误不看数字很难发现。

### 3.2 写视频：逐帧 PNG → 直接喂 ffmpeg 管道

官方实现把每一帧写成 PNG 存到临时目录，再用 concat demuxer 读回来编码
（全量会产生约 **240 万个临时 PNG**）。改成 rawvideo 管道后：

| 隔离实验（同一批帧） | 平均差 | 最大差 | 结论 |
| --- | --- | --- | --- |
| png vs png（同参数重复编码） | 0.000 | 0 | 编码器确定性 ✓ |
| **png vs pipe（写后端差异）** | **0.000** | **0** | **管道写法与官方逐帧 PNG 逐位一致** ✅ |

### 3.3 warp 换 cv2 的保真度（诚实说明）

| 对比 | 平均差 | 最大差 | >2 灰度级占比 |
| --- | --- | --- | --- |
| 解码前的内存 ROI 帧 | **0.503** | 3 | **0.001%** |
| 编码后的 mp4 产物 | 2.255 | 35 | 35% |

- 换 warp 只让**内存中的 ROI 帧**差 0.5 个灰度级（最大 3，十万分之一个像素差超过 2），
  这是两种双线性重采样的最后一位取整差异。
- 但 h264 是有损的：这么小的输入差会改变编码器的率失真决策，**产物层面放大到平均 2.3 级**。
  这一放大与写后端无关（pipe 与 png 两条路径给出完全相同的差异数字）。
- 判断：2.3/255 ≈ 0.9%，与压缩噪声同量级，对训练（还要转灰度、归一化、随机裁剪增广）
  影响可忽略；但它确实意味着**产出的 ROI 视频与官方预处理不是逐位可比的**。
  因此保留 `--warp-backend skimage --write-backend png` 作为退回官方行为的开关，
  汇报时应写明采用的设置。

### 3.4 其它已落地的优化

| 优化 | 位置 | 实测/依据 |
| --- | --- | --- |
| 关键点阶段支持**断点续跑** | `detect_landmark.py` | 原实现没有任何跳过逻辑，任何中断都让最慢的一步（8 rank 下仍要数小时）从头再来。现在：产物存在则用 `pickle.load` 校验后跳过；写入改为 `tmp + os.replace` 原子替换，避免半截 pkl |
| 预解码帧缓存 | `build_frame_cache.py` + `utils.FrameCache` | 训练数据路径 **0.83 → 0.67 s/步**（真实规模 A/B）。**⚠️ 注意**：这是隔离 A/B 的数字，**交付的那次训练并没有用上缓存**（构建时索引发布失败，训练回退在线解码）；真实训练实测 0.33 秒/步且 GPU 利用率 100%，说明该负载是 **GPU 瓶颈**，缓存收益有限。详见 `../results/02_微调与解码/配置与结果.md` §3.1 |
| `Normalize` 显式转 float32 | `avhubert/utils.py` | 原来 uint8 与 python float 相减被提升为 **float64**，而出口本来就要 `astype(np.float32)`；float64 中间结果让每个 500 帧 clip 多背 36.8 MB 拷贝（float32 18.4 MB），8 个 worker 都受影响 |

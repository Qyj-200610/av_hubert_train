# 预处理流水线并行化方案（Plan B）

> **背景**：LRS2 全量预处理（48,164 条）在 8 核实例上耗时过长，根因是
> `pipeline_lrs2.sh` 里各 rank **串行**执行，**8 核实际只用 1 核**。
> 本文档给出精确改动、实测依据、风险与执行清单。
>
> 状态：**已执行**（3.1 主改动已落地并验证；§2 的耗时估算经实测修正，
> 详见文末 [§8 执行记录与实测修正](#8-执行记录与实测修正)）

---

## 1. 问题陈述

`scripts/pipeline_lrs2.sh` 的 `all` 模式当前实现：

```bash
if [[ "${NSHARD}" -gt 1 ]]; then
  echo "提示：多分片时建议把 audio/landmark/mouth 按 rank 提交到多卡/多进程并行执行。"
  for ((r=0; r<NSHARD; r++)); do step_audio    "$r"; done   # ← 串行
  for ((r=0; r<NSHARD; r++)); do step_landmark "$r"; done   # ← 串行
  for ((r=0; r<NSHARD; r++)); do step_mouth    "$r"; done   # ← 串行
else
  step_audio 0; step_landmark 0; step_mouth 0
fi
```

脚本自己打印的提示已经指出了问题（「建议把 audio/landmark/mouth 按 rank 提交到
多卡/多进程并行执行」），但 `all` 模式并未真正并行。

**关键点**：`step_audio` / `step_landmark` / `step_mouth` 都接受 `rank` 参数，
且内部按 `num_per_shard = ceil(len(fids)/nshard)` 切片。也就是说
**`nshard` 个 rank 的切片互不重叠，其结果互不依赖，天然可并行**。
串行执行是纯粹的等待，不是算法要求。

## 2. 实测依据

全量运行（48,164 条，实例 8 核）实测数据：

| 阶段 | 实测进度 | 速率 | 推算总耗时 |
| --- | --- | --- | --- |
| 2. 抽音频 | 100%（48,164 文件） | 约 11.4 it/s | **约 40 分钟** |
| 3. dlib 关键点 | 9.3%（4,457 文件） | **1.07 it/s** | **约 75 分钟** |
| 4. 唇部 ROI | 未开始 | 预计更慢（每 clip 一次 ffmpeg 转码） | 约 60–90 分钟 |
| 5. 数帧 | 未开始 | — | 几分钟 |
| 6. manifest | 未开始 | — | 约 1 分钟 |

**合计约 3 小时**（此前的「2 小时」估计偏低，已更正）。

> ⚠️ **上表已证实有误，见 [§8](#8-执行记录与实测修正)**：表中「抽音频/关键点」的
> 推算把**单个 rank 的耗时**当成了整个阶段的耗时（未乘 NSHARD=8）。
> 实测串行关键点约 **30 小时**（不是 75 分钟），全量串行总计约 **40 小时**。
> 并行化的加速比结论（5–6×）成立，但绝对耗时需按 §8 修正值理解。

### 并行化后的预期

当前每一步在任一时刻只有 1 个 rank 在跑，即单核利用率。8 核并行后：

| 阶段 | 串行 | 并行（8 rank） |
| --- | --- | --- |
| 抽音频 | 约 40 分钟 | 约 **6–8 分钟** |
| 关键点检测 | 约 75 分钟 | 约 **12–15 分钟** |
| 唇部 ROI | 约 60–90 分钟 | 约 **10–15 分钟** |
| **合计** | 约 3 小时 | **约 30–40 分钟** |

> 注意：并行效率不会线性到 8×。`detect_landmark.py` 内部用 dlib 做 68 点检测，
> 单进程本身也有一定并行度；且 48,164 个小文件的磁盘 I/O 会成为新的瓶颈。
> 因此上表按 5–6× 有效加速估计，而非 8×。

## 3. 改动内容

### 3.1 主改动：`all` 模式改为并行 + `wait`（位于文件末尾 `case` 段）

**改前**：

```bash
  all)
    step_prepare
    if [[ "${NSHARD}" -gt 1 ]]; then
      echo "提示：多分片时建议把 audio/landmark/mouth 按 rank 提交到多卡/多进程并行执行。"
      for ((r=0; r<NSHARD; r++)); do step_audio "$r"; done
      for ((r=0; r<NSHARD; r++)); do step_landmark "$r"; done
      for ((r=0; r<NSHARD; r++)); do step_mouth "$r"; done
    else
      step_audio 0; step_landmark 0; step_mouth 0
    fi
    step_frames
    step_manifest
    ;;
```

**改后**：

```bash
# 并行执行同一阶段的所有 rank，并收集失败状态
# 用法: run_ranks_parallel <step_fn_name>
run_ranks_parallel() {
  local step_fn="$1"
  local pids=() failed=0

  for ((r=0; r<NSHARD; r++)); do
    "${step_fn}" "$r" &
    pids+=($!)
  done

  for ((i=0; i<${#pids[@]}; i++)); do
    if ! wait "${pids[$i]}"; then
      echo "错误：${step_fn} rank $i 失败 (pid ${pids[$i]})" >&2
      failed=1
    fi
  done

  if [[ "${failed}" -ne 0 ]]; then
    echo "错误：${step_fn} 存在失败的 rank，终止流水线。" >&2
    exit 1
  fi
}

  all)
    step_prepare

    # 阶段级并行：每个阶段内 NSHARD 个 rank 同时跑，跑完再进下一阶段
    log "step 2/6  并行抽音频（${NSHARD} 个 rank）"
    run_ranks_parallel step_audio

    log "step 3/6  并行检测人脸关键点（${NSHARD} 个 rank）"
    run_ranks_parallel step_landmark

    log "step 4/6  并行裁切唇部 ROI（${NSHARD} 个 rank）"
    run_ranks_parallel step_mouth

    step_frames
    step_manifest
    ;;
```

**设计要点**：

- **阶段间保持顺序**：先等所有 rank 的音频做完，再做关键点。因为
  `step_frames` 需要全部产物就绪。
- **保留 `wait` 的退出码检查**：任一 rank 失败即终止，避免带着残缺数据
  跑后续阶段（否则失败会在几小时后才暴露）。
- **不使用 `wait`（无参数）**：无参数 `wait` 无法区分哪个 rank 失败。

### 3.2 可选改动：限制单次 ffmpeg 线程数

并行后 8 个 ffmpeg 同时启动，每个默认会吃掉多线程，可能引发 CPU 争抢。
`step_audio` 内的 ffmpeg 调用可加 `-threads 1`：

```bash
# step_audio 内的 subprocess.call（改前）
subprocess.call([ffmpeg, '-i', src, '-f', 'wav', '-ar', '16000', '-ac', '1', '-vn', '-y', dst,
                 '-loglevel', 'quiet'])

# 改后
subprocess.call([ffmpeg, '-threads', '1', '-i', src, '-f', 'wav',
                 '-ar', '16000', '-ac', '1', '-vn', '-y', dst, '-loglevel', 'quiet'])
```

> 该项标记为**可选**：短视频转码本身很轻，8 并发未必需要限线程。
> 建议先按 3.1 跑，若观察到 CPU 争抢严重再加。

## 4. 风险与缓解

| # | 风险 | 严重度 | 缓解措施 |
| --- | --- | --- | --- |
| 1 | **重跑会丢弃已完成进度**（音频 40 分钟成果作废） | 中 | 重跑前确认当前进度；若音频已 100%，可考虑只重跑 landmark/mouth（见 §5 步骤 3） |
| 2 | 8 个进程并发写同一目录，可能导致 I/O 瓶颈 | 中 | 产物文件名含 fid，各 rank 切片不重叠，**无写入冲突**；仅需接受 I/O 竞争 |
| 3 | 内存占用上升（8 个 Python 进程各加载 dlib/numpy） | 低 | 实例 251 GB 内存，实测远未吃紧 |
| 4 | 任一 rank 失败可能导致整批白跑 | 高 | `run_ranks_parallel` 检查每个 pid 的退出码，失败立即 `exit 1`；且建议先做 §5 步骤 1 的小样本并行验证 |
| 5 | 改动引入新 bug | 中 | 改动仅限 `case` 段与新增函数，不触碰任何算法逻辑；且先经小样本验证 |
| 6 | 当前正在运行的任务需先停止 | 低 | `pkill -f pipeline_lrs2.sh`，并清理半成品 |

### 为什么建议「先小样本验证」

本项目此前多次因**未先验证就全量运行**而浪费机时（例如
`sentencepiece vocab_size` 在小样本下必然失败、`LD_LIBRARY_PATH` 反噬 ffmpeg）。
并行化改动同理：先用 `LIMIT=30` 验证并行逻辑正确、产物齐全，再全量跑。

## 8. 执行记录与实测修正

执行日期：2026-10-08；实例：恒源云 RTX 3090。编排脚本见仓库根目录
`run_parallel_pipeline.py`（连接 / 上传 / 验证 / 全量 / 监控 / 验收六个子命令）。

### 8.1 实际落地范围

| 项 | 状态 |
| --- | --- |
| §3.1 主改动（`run_ranks_parallel` + `all` 改并行） | ✅ 已实施并验证 |
| §3.2 可选改动（ffmpeg `-threads 1`） | ⏸ **未实施**——音频阶段本次直接复用已有产物，未触发；按文档建议"先观察再加" |
| 算法逻辑（`detect_landmark.py` / `align_mouth.py` / `count_frames.py`） | ✅ **零改动**（方案承诺"不触碰算法逻辑"，遵守） |

函数位置与方案片段略有不同：`run_ranks_parallel` 定义在 `# ---------- 入口 ----------`
**之前**、`case` 语句**之外**。因为 bash 的函数必须先定义后调用，若照方案片段那样
写在 `case ... in` 内部（`all)` 之前）会直接语法错误。已用 `bash -n` 验证。

### 8.2 关键环境修正：`nproc` 会骗人

| 指标 | 值 | 说明 |
| --- | --- | --- |
| `nproc` | **64** | 宿主机可见核数 |
| cgroup CPU 配额 | **8** | `cpu.cfs_quota_us/cpu.cfs_period_us = 800000/100000` |

**结论：`NSHARD=8` 是对的，但理由不是"机器有 8 核"，而是"容器配额只有 8 核"。**
若按 README 原先"云上可用 `$(nproc)`"的建议设 `NSHARD=64`，只会带来上下文切换
开销而不会更快。README 该处已同步更正。

### 8.3 步骤 1 小样本验证：通过

一处**主动偏离方案原文**：方案步骤 1 要求 `rm -rf /hy-tmp/lrs2_data` 后再跑
`LIMIT=30`，这会把已 100% 完成的 48,164 个音频（串行耗时约 67 分钟）直接丢掉。
但 `step_audio` 内部本来就有 `if os.path.isfile(dst): continue`（`pipeline_lrs2.sh:149`），
产物按 fid 命名且各 rank 切片不重叠，重跑是**秒级跳过**。故改为：

- 小样本验证落在独立目录 `/hy-tmp/lrs2_parcheck`（与全量产物完全隔离）；
- 全量运行继续用 `/hy-tmp/lrs2_data`，音频阶段秒级跳过，只重跑 landmark / mouth。

这正是方案 §4 风险 1 缓解措施里写的"若音频已 100%，可考虑只重跑 landmark/mouth"，
属于方案授权范围内的偏离。

**通过标准逐条核对**（`LIMIT=30`，退出码 0）：

| 检查项 | 期望 | 实测 |
| --- | --- | --- |
| `audio/` `landmark/` `video/` 文件数 | 各 90 | 90 / 90 / 90 ✅ |
| `nframes.audio` / `nframes.video` 行数 | 各 90 | 90 / 90 ✅ |
| `data/` 文件数 | 9 | 9 ✅ |
| `data/train.tsv` 第二行列数 | 5 | 5 ✅ |
| **额外**：每条 fid 三类产物是否齐全 | — | 90 条 fid，缺失 audio 0 / landmark 0 / video 0 ✅ |

最后一项是方案没要求的**更强校验**：直接按 `file.list` 逐条 fid 检查三类产物存在性，
比"数文件个数"更能发现"某 rank 少写 / 写串名"的问题。

### 8.4 额外单测：失败路径

小样本验证只覆盖了顺利路径，而方案 §4 风险 4（"任一 rank 失败可能导致整批白跑"）
恰恰依赖失败路径。故把函数从脚本里 `sed` 抽出来，用桩函数单独测
（`test_run_ranks_parallel.py`）：

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 4 个 rank 全成功 | 不终止，退出码 0 | 0 ✅ |
| 4 个 rank 全失败 | 报错并退出 1 | 1，5 条错误信息 ✅ |
| **仅 rank 2 失败** | 退出 1 **且点名 rank 2** | 1，输出 `rank 2 失败` ✅ |
| `NSHARD=1` 边界 | 正常，退出码 0 | 0 ✅ |

第三个用例正是方案坚持"不用无参数 `wait`"的理由：能精确定位到失败的是哪个 rank。

### 8.5 实测耗时修正（重要）

**串行基线（实测，非估算）**：

| 阶段 | 实测串行耗时 | 方案原文 | 偏差 |
| --- | --- | --- | --- |
| 抽音频 | 单 rank 8:24 × 8 ≈ **67 分钟** | 约 40 分钟 | 偏低 1.7× |
| dlib 关键点 | 2.236 s/clip × 48,164 ≈ **30 小时** | 约 75 分钟 | **偏低约 24×** |
| 唇部 ROI | 1.2 s/clip × 48,164 ≈ **16 小时** | 约 60–90 分钟 | **偏低约 12×** |
| 数帧 + manifest | 几分钟 | 几分钟 | 一致 |
| **合计** | **约 47 小时** | 约 3 小时 | **偏低约 15×** |

偏差根因：方案表格把**单个 rank 跑了多少**当成了整个阶段的总量
（如"9.3% = 4,457 文件"其实只是 rank 0 的分片），漏乘了 NSHARD。
唇部 ROI 的单 clip 成本用真机探针测得（12 clip 共 15 秒，含 ffprobe、
逐帧 warpAffine/cut_patch、逐帧写图、ffmpeg concat 编码的全部开销）。

**并行实测（8 rank，采 3 次、间隔 5 分钟）**：

| 采样 | 关键点文件数 | 并行吞吐 | 加速比 |
| --- | --- | --- | --- |
| 20:36 | 5,570 (11.6%) | — | — |
| 20:41 | 6,372 (13.2%) | 2.7 it/s | **5.9×** |
| 20:46 | 7,261 (15.1%) | 3.0 it/s | **6.6×** |

- 并行加速比 **6–6.6×**，与方案"5–6× 有效加速（而非 8×）"的预期**吻合**，
  说明 8 核配额 + 磁盘 I/O 竞争导致的损耗判断正确。
- 但关键点阶段按此速率的**实际残余耗时约 3.8–4 小时**，而不是方案 §2 写的 12–15 分钟。
  **并行化本身有效，方案的结论对、绝对数字错。**
- 8 个 rank 各占约 88–90% CPU，合计约 7.2/8 核，配额基本吃满。

**各分片速率不均（值得注意）**：同一时刻 8 个 rank 的瞬时速率在
**0.344–0.476 it/s** 之间（相差约 40%）。分片是按 `file.list` 顺序切的，
各分片包含的说话人/视频时长不同，因此**阶段耗时由最慢的那个 rank 决定**，
而不是平均值——ETA 要按 `max(各 rank 剩余时间)` 估，不能按总量除总吞吐。

**唇部 ROI 并行预期**：单进程实测 1.2 s/clip，8 rank 并行后预计约 **2–3 小时**
（该阶段 CPU 较轻、I/O 较重，加速比可能低于关键点的 6×）。
附带一个好消息：`align_mouth.py:231` 有 `if os.path.exists(dst_pathname): continue`，
**该阶段可断点续跑**（而 `detect_landmark.py` 没有跳过逻辑，必须整段重算）。
